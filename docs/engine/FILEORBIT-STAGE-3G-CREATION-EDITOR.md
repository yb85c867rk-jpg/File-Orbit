## Context flow

Trusted issued context is threaded through:

1. `collectDirectorySelection`:
   - `policyContext`, optional caller `maxNodes`;
   - omitted context = free 300;
   - explicit paid = 1,000;
   - actual collected nodes checked including root.
2. `prepareCreateMapCandidate`:
   - same context/caller policy before folder/file materialization;
   - root counted exactly once;
   - nested/empty folders and attachment staging remain candidate-local.
3. `validateEditorAdmission` and all validators:
   - actual tree count via `countTreeNodes`;
   - context limit and optional caller tightening;
   - no declared count or document metadata authority.
4. Rename, metadata, add-child, folder edit, data edit, delete:
   - every command receives `policyContext`/`maxNodes`;
   - existing oversized tree is admitted/rejected **before** any reducing candidate is built.
5. History replay validation:
   - optional context/caller budget passed into replay admission as a directly required caller.
6. `action.js` installation wrappers:
   - pass context to command/history builders; installation/layout behavior is not claimed as complete paid editing.

Omitted `maxNodes` is `undefined`, not 300; a paid context is not accidentally capped at 300. Caller budgets may only tighten. Forged contexts return `invalid-policy-context`. No authority is read from URL, storage, document fields, or UI flags.

## Command/candidate boundary

Every command remains preparation-only:

- no live tree mutation;
- no history/identity/attachment/persistence mutation;
- candidate tree built by clone;
- stale dataset/revision rejected before construction;
- root protection retained;
- attachment limits unchanged (20 MiB/file, 100 MiB/map).

Free context encountering a 1,000-node document cannot delete/rename/metadata-edit it to bypass admission. Paid context can prepare those commands. Delete of a paid-size subtree still requires paid admission and returns a candidate.
